# 문서 관리

## 원칙

작업 상태·우선순위·재개 지시는 [GitHub 이슈](https://github.com/loading1031/2nd-if/issues)에 둔다. 제품 요구사항과 주요 결정은 저장소 마크다운 한 곳에 기록한다. 모든 기능에 기획·디자인·개발 문서 세 벌을 만들지 않는다.

## 위치

| 위치 | 용도 |
|---|---|
| `docs/specs/<topic>.md` | 주제별 요구사항·사용자 흐름·결정·완료 기준 |
| `docs/specs/index.md` | 스펙 탐색 색인. 작업 상태는 이슈로 연결 |
| `docs/design/` | 독립적으로 필요한 디자인 명세·리더 스타일 |
| `docs/dev/` | 배포·운영 가이드와 기존 구현 참고. 새 작업마다 만들지 않음 |
| `docs/plans/` | 여러 작업에 걸친 전환·실행 계획이 필요한 경우 |
| `docs/history/`, 기존 `docs/log.md` | 과거 기록. 매 작업마다 로그 갱신 불필요 |

## 작업 방식

1. 관련 이슈와 스펙을 읽는다. 이슈가 없으면 요청 범위 안에서 목표·완료 기준을 작성한다. 작업 관리 대상이 아닌 오타·작은 설정 수정까지 이슈 생성을 강제하지 않는다.
2. 기존 스펙에 충분히 담을 수 있으면 그 문서를 수정하고, 길어지거나 독립적인 주제일 때만 분리한다.
3. 사용자가 결정한 것, 제안, 미정 사항을 구분한다. 출처를 확인하지 않은 사실은 확인 필요로 표시한다.
4. 바뀐 결정과 직접 관련된 문서·코드만 대조한다. 전체 문서 그래프를 순회하거나 역링크를 일괄 생성하지 않는다.
5. 이슈에 변경 요약·검증·남은 일·다음 행동·브랜치/PR/커밋을 남긴다. 같은 상태를 백로그 파일·작업지시서·결정 로그에 복사하지 않는다.

새 링크는 `[설명](상대경로.md)` 형식이다. 기존 위키링크는 해당 문서를 실제로 고칠 때 필요한 부분만 변환한다. 문서를 일괄 이동·삭제하지 않는다. 디자인·운영 가이드를 합치는 것은 내용의 유지 가치와 중복을 확인한 뒤 결정한다.

## 주제 문서 최소 형식

```markdown
# 주제

## 결론
확정된 방향 또는 현재 제안.

## 요구사항과 사용자 흐름
필요한 동작·오류·권한 조건.

## 주요 결정
무엇을 왜 선택했는가. 미정은 구분한다.

## 완료 기준
사용자 관점에서 확인할 결과.

## 관련 자료
관련 이슈와 필요한 디자인·운영 가이드 링크.
```

기존 문서 형식을 이 템플릿으로 강제 변환하지 않는다. 의미 있는 설계 결정은 스펙에, 구현 파일 목록과 진행 메모는 이슈·PR에 둔다.

## planning 플러그인과의 차이

원본 `planning`의 한 주제씩 결정하기, 검증한 사실만 쓰기, 명시적 커밋·이슈 연결을 재사용한다. 이 프로젝트의 작업지시서·백로그는 GitHub 이슈이며 `backlog.md`, `work-orders.md`, `log.md` 동시 갱신 절차를 사용하지 않는다. Git 예외는 [workflow.md](workflow.md)에 있다.
