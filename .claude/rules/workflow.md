# Git·작업 워크플로우

## 브랜치

- 통합·기획 기준은 `dev`, 릴리스 대상은 `main`이다. 모든 일반 PR의 base는 `dev`, 릴리스만 `dev` → `main`이다.
- 새 작업은 최신 원격 `dev`에서 분기한다. 기획은 `plan/<issue>-<slug>`, 코드는 `feat|fix|refactor/<issue>-<slug>`, 설정은 `chore/<issue>-<slug>`를 사용한다.
- Codex 환경에서 접두어를 요구하면 `codex/plan/<issue>-<slug>`처럼 `codex/`를 앞에 붙인다. 기존 작업 브랜치는 이름을 일괄 바꾸지 않는다.
- `dev`·`main`에 `feat`/`fix`/`refactor`/`test`/`design` 커밋을 직접 만들지 않는다. 의미 있는 기획 변경도 작업 브랜치에서 한다. 결정이 바뀌지 않는 작은 문서·설정 수정은 통합 브랜치에서 가능하다.
- 브랜치를 바꾸기 전 변경 파일과 다른 워크트리를 확인한다. 다른 작업 WIP를 임의로 stash하거나 통합하지 않는다. 같은 폴더에 WIP가 있으면 해당 파일을 보존한 채 충돌하지 않는 작업만 진행한다.

## 커밋

- 접두어: `docs`, `feat`, `fix`, `refactor`, `test`, `chore`, `design`. 메시지는 한국어 50자 이내를 권장하고 변경 이유가 드러나게 쓴다.
- 관련 파일만 이름으로 스테이징한다. 전체 스테이징 옵션이나 저장소 전체 경로를 사용하지 않는다. 비밀값·계정 문서·Terraform state/plan을 포함하지 않는다.
- 작업 브랜치의 새 커밋 본문 끝에는 `Refs: #<이슈 번호>`를 넣는다. 이슈가 없는 작은 수정은 `Refs: maintenance`로 명시한다. GitHub 이슈가 작업 식별자이므로 별도 백로그 ID가 필요하지 않다.
- 커밋에서 이슈를 닫는 키워드를 사용하지 않는다. 이슈 종료는 PR 본문 `Closes #N`으로 한다.
- 기획과 제품 코드의 독립적인 변경은 분리한다. 문서·도구·검사가 하나의 운영 규칙 전환을 이루면 하나의 설정 변경으로 묶을 수 있다.
- amend는 사용자가 요청한 경우에만, 원격에 게시하지 않은 커밋에 한한다. 수정 후에는 기본적으로 새 커밋을 만든다.
- 저자 표시는 현재 시스템 지시를 따르며, 지시가 없으면 추가하지 않는다. 모델·이메일을 임의로 만들어 쓰지 않는다.
- 기존 스테이징 파일을 확인하고 작업 범위 밖 변경을 커밋하지 않는다. 커밋·push·PR 생성은 해당 작업에 대한 사용자 승인 범위에서만 수행한다.

## PR·병합·정리

- PR에는 문제, 결과 동작, 검증, 관련 이슈를 쓴다. 병합은 머지 커밋 방식으로 한다.
- push·PR 병합은 사용자 요청 범위를 확인한다. 요청하지 않은 릴리스·배포를 수행하지 않는다.
- 워크트리는 `git worktree list`의 실제 경로로 확인한다. 변경 유무와 통합을 확인한 후 일반 `git worktree remove <path>`와 `git branch -d <branch>`를 사용한다.
- 작업을 버리는 강제 제거·강제 브랜치 삭제·강제 push·히스토리 재작성은 자동 수행하지 않는다. 원격 브랜치는 유지한다.
- 충돌은 순서·권한·동작을 검토해 해결한다. import·URL·설정을 무조건 합집합으로 합치지 않는다.

## 리뷰와 머지 조건

- `dev`·`main`은 `test`, `policy`, `review-complete` 통과와 모든 리뷰 대화의 해결을 요구한다. 관리자에게도 동일하게 적용하고, 정식 승인 개수는 요구하지 않는다.
- `review-complete`는 최신 PR head에 대한 Codex 코드 리뷰 완료를 확인한다. 미수신·실행 중·실패·이전 커밋·알 수 없는 요약 형식은 통과하지 않는다. 추가 보안 리뷰가 요청됐다면 그것도 완료돼야 한다.
- 리뷰 대화는 GitHub의 Require conversation resolution으로 차단한다. 체크 통과만으로 미해결 대화를 무시하거나 자동 해결하지 않는다.
- 새 커밋이 올라오면 이전 리뷰는 체크를 통과시키지 못한다. Codex의 검토 트리거가 PR 생성 시로 설정된 경우 새 커밋에는 별도 재검토 요청이 필요하다.
- 구현: `.github/workflows/review-gate.yml`, `scripts/review-gate.ts`. `npm run build:review-gate`로 실행 모듈을 재생성한다. 쓰기 토큰으로 PR head 코드를 실행하지 않고 기본 브랜치의 검사 코드만 사용한다.
- 기본 브랜치에 워크플로가 설치돼야 댓글/리뷰 이벤트를 처리할 수 있다. 설치 전에는 누락 체크를 통과로 처리하지 않는다. 수동 재평가는 Actions → Review gate → Run workflow의 PR 번호 입력을 사용한다.
- 봇의 요약 v1은 현재 관측한 형식이다. 형식이 바뀌면 실패 상태를 유지하고 검사 코드를 수정한다. 단순 👍 반응이나 다른 계정이 쓴 요약 문구로 통과시키지 않는다.

## 공통 검사

- 메시지 검사: `python3 scripts/check_git_policy.py commit <message-file> --branch <branch>`.
- 로컬 설치: `python3 scripts/install_git_hooks.py`. 현재 checkout의 hooks 디렉터리에 `commit-msg`만 설치하며 기존 pre-commit을 유지한다. 알 수 없는 기존 commit-msg가 있으면 덮어쓰지 않는다.
- 일시적인 Git 인덱스 잠금 생성 실패는 `python3 scripts/commit_with_retry.py`를 통해 최대 30초간 대기·재시도한다. 대상 `index.lock`의 경합성 생성 오류만 재시도하며, 그 외 오류는 반환한다. 기존 훅은 유지하고 커밋 명령을 래핑한다.
- CI: `.github/workflows/git-policy.yml`이 PR base·새 커밋 메시지를 검사한다. GitHub required check 지정은 별도 저장소 설정이며 자동으로 완료됐다고 보고하지 않는다.
- 브랜치 접두어를 과거 이력에 소급하지 않는다. 이미 base에 있는 커밋과 Git 병합 커밋은 메시지 검사 대상에서 제외한다. 이관 시점 dev `6e998bd57bd0fae0db997e2413a50b45f6697f5f`와 OCI `77ad0301342b552f145f7b36f4a2c5d343770d97`의 과거 이력도 고정 SHA 기준으로 제외한다. 기준 이후 새 커밋에는 규칙을 적용하며, 릴리스 PR에서도 새 커밋의 Refs를 검사한다.
- 로컬 훅은 이 checkout에서 설치해야 실행된다. Claude 전용 실행 전 훅이 Codex에서도 실행된다고 가정하지 않는다. 대량 스테이징 금지는 에이전트 지침이며 메시지 훅의 검사 항목이 아니다.
- Git 훅이 공유되는 과거 브랜치·워크트리에 검사 스크립트가 없으면 메시지 검사는 실행하지 않는다. 전환 파일이 들어온 브랜치부터 적용한다.

## 외부 planning 원본

기준 원본은 `loading1031/claude-plugins`의 `plugins/planning`, 도입 시점 `9f42ac7518c679bdc4f4b35102f50b57ab58ca5b`다. 원본 업데이트는 이 파일·문서 규칙과 비교해 명시적으로 반영한다. 프로젝트 예외를 덮어쓰는 자동 동기화를 하지 않는다.

원본의 `main` 기획 통합/`dev` 코드 통합 모델 대신 이 프로젝트는 모두 `dev`에 통합한다. 원본의 백로그 파일·로그·작업지시서 절차 대신 이슈를 사용한다. 따라서 원본 checker를 그대로 복사해 호환된다고 취급하지 않는다.
