# GitHub 이슈 중심 작업 관리로 전환
Created: 2026-10-15

## 결론

작업 상태·재개 지시·완료 근거는 GitHub 이슈에, 제품의 지속적인 요구사항·설계는 저장소의 일반 마크다운에 둔다. 기능마다 기획/디자인/개발 문서 세 벌과 양방향 위키링크를 만들던 규칙은 해제한다. 기존 문서와 Git 이력은 보존하고, 실제로 다시 다루는 주제부터 정리한다.

이번 요청에서 수행하는 범위는 과거 이슈 이관과 전환 계획 작성까지다. 아래 설정 전환, 코드 통합, 커밋·push·PR·브랜치 삭제는 후속 작업이다.

## 1. 과거 이력 고정 — 이번 작업

- 기능 단위 구현 이력 10건은 닫힌 이슈로, 진행/기획 후보 8건은 열린 이슈로 기록한다.
- 각 이슈에 커밋과 불변 스냅샷 문서 링크, 남은 일, 재검증 범위를 담는다.
- 실제 원격 브랜치가 있는 OCI 작업은 브랜치 링크를 남긴다. 로컬 브랜치·stash·미커밋 작업은 원격 링크를 꾸며내지 않는다.
- 과거 완료 이슈는 당시 코드 반영의 기록이며 현재 테스트 통과·운영 배포 완료를 보증하지 않는다.
- 작업 이력 색인에서 이슈 번호와 범위를 한 번에 찾을 수 있게 한다.
- 로컬 관리자 계정 문서의 내용, 환경변수, Terraform state/plan 내용, 키 등은 이슈 본문으로 복사하지 않는다.

완료 기준: 생성 이슈의 본문·상태를 GitHub에서 다시 조회하고 원격 브랜치 링크가 감사 결과와 일치함을 확인한다.

## 2. 미커밋·stash 작업을 먼저 분리 — 전환 착수 전

1. 현재 세계관 WIP와 이미 변경된 설정 파일을 구분해 보존한다. 관련 파일만 명시해 커밋하며 사용자의 다른 변경을 섞지 않는다.
2. 스프라이트 stash는 격리된 작업 공간에서 검토하고 스프라이트, 배포, Terraform 변경을 나눈다. 현재 작업 트리에 일괄 적용하지 않는다.
3. OCI 브랜치는 dev와 커밋·내용을 대조해 필요한 인프라 변경만 선정한다. 중복 기능 커밋을 전체 병합하지 않는다.
4. 작업 브랜치와 열린 이슈를 연결하고, 승인된 원격 게시 시 이슈에 해당 브랜치 링크를 추가한다.

완료 기준: 모든 로컬 WIP가 어느 이슈에 속하는지 식별되고, 통합 대상과 보존 대상이 구분됨. stash·브랜치는 보존 확인 없이 삭제하지 않음.

## 3. 문서 운영을 한 곳으로 정리

역할을 다음처럼 나눈다.

| 위치 | 담는 것 | 담지 않는 것 |
|---|---|---|
| GitHub 이슈 | 목표, 범위, 완료 기준, 현재 상태, 다음 행동, 브랜치/PR/커밋 | 전체 제품 스펙 복사본 |
| 기존 `docs/specs/<topic>.md` | 해당 기능의 지속적인 요구사항·사용자 흐름·주요 결정 | 매 작업마다 만드는 별도 개발 지시서 |
| `docs/design/` | 리더 스타일 등 독립적으로 필요한 디자인 명세 | 모든 기능에 의무적으로 만드는 디자인 문서 |
| `docs/dev/` | 유지 가치가 있는 배포·운영 가이드와 과거 구현 참고 | 코드 파일·함수 목록의 반복 기록 |
| `docs/history/` | 과거 이관 색인 | 지속적인 상태 관리용 백로그 복제본 |

- 기존 문서 위치를 유지해 이슈의 링크가 깨지지 않게 한다. 일괄 이동·삭제하지 않는다.
- 새 링크는 일반 마크다운 상대 링크를 사용한다. 역링크는 필수가 아니다.
- 손대는 문서의 `[[...]]`만 점진적으로 바꾼다. 이전 문서 전체를 한 번에 변환하지 않는다.
- 한 주제의 의미 있는 결정은 해당 스펙 한 곳에 기록하고, 변경 이유는 Git/이슈에 남긴다.
- GitHub 이슈를 작업지시서로 사용하므로 `backlog.md`, `work-orders.md`, 결정 로그를 같은 내용으로 동시에 갱신하는 의무를 두지 않는다. 기존 `docs/log.md`는 과거 기록으로 보존한다.
- 기존 인덱스는 스펙 탐색용으로 유지하고, 작업 상태는 이슈로 연결한다.

완료 기준: 새 작업 하나가 이슈와 필요한 스펙 한 곳만으로 재개 가능하며, 세 계층 문서·역링크·백로그·로그 동시 갱신이 요구되지 않음.

## 4. Claude·Codex 지침과 스킬 연결

1. 루트 `AGENTS.md`와 `CLAUDE.md`를 짧은 진입점으로 추가한다. 공통 프로젝트 규칙은 같은 저장소 파일을 참조해 유지한다.
2. Django/HTMX/TipTap/Tailwind/DaisyUI/패턴 라이브러리 규칙은 보존하고, 파일 종류별로 필요한 규칙을 읽게 한다.
3. `.claude/rules/docs.md`, `workflow.md`, 메인 규칙에서 Obsidian/삼중 문서/역링크 의무와 상충하는 Git 절차를 교체한다.
4. 기존 `/doc`, `/feature`, `/scenario`, `/merge`, `/commit`과 `.agents/skills/source-command-*`를 함께 점검한다. 문서·Git 동작은 새 규칙으로 통일하고, 기존 명령은 그 규칙을 참조하는 얇은 진입점으로 바꾸거나 대체 안내를 둔다. 테스트 생성 자체는 유지한다.
5. 새 planning의 원칙은 재사용하되, `CLAUDE.md` 전용 설정 읽기와 Claude 도구/훅 호출은 Codex용으로 연결한다. 외부 사용자 홈 절대 경로에만 의존하지 않고 설치 가능한 원본·동기화 기준을 기록한다.
6. 이미 발견한 `.Codex/rules/` 잘못된 경로, 허위 `Codex Opus` 작성자, 워크트리 고정 경로와 미학 리뷰어 메모리 경로를 수정한다. deploy 이관은 실제 배포 대상 확인 후 진행한다.
7. 새 planning 원본이 요구하는 백로그 파일·기획 브랜치 절차와 위의 이슈 중심 운영 간 차이를 명시적인 프로젝트 예외로 정리한다. 원본과 다른 절차를 두고 그대로 호환된다고 표시하지 않는다.

완료 기준: 두 에이전트에서 같은 작업을 요청했을 때 같은 문서 위치·Git 규칙이 선택되고, 삭제한 Notion/Gemini/Obsidian 의무나 존재하지 않는 경로가 다시 등장하지 않음.

## 5. Git 정책 정합성 및 강제 수단

- 제안: 현 GitHub 기본 브랜치 `dev`를 작업·기획의 통합 기준으로 유지한다. `main`은 릴리스 대상으로 둔다. 전환 작업에 기본 브랜치 변경을 끼워 넣지 않는다.
- 기획 작업은 `plan/<issue>-<slug>`, 코드 작업은 `feat|fix|refactor/<issue>-<slug>`에서 진행하는 프로젝트 규칙을 명시한다. Codex의 환경별 브랜치 접두어 요구와도 정합성을 확인한다.
- 코드와 기획 PR은 `dev`로, 릴리스는 `dev` → `main`으로 보낸다.
- 커밋은 관련 파일만 명시해 스테이징하고 접두어와 `Refs: #N`을 사용한다. 이슈 종료는 PR 본문 `Closes #N`에서 한다.
- 요청 없는 amend/push, 강제 워크트리 제거·브랜치 삭제는 하지 않는다. 합쳐진 로컬 브랜치는 보존 여부 확인 후 `-d`, 원격 브랜치는 유지한다.
- 새 planning의 Claude `PreToolUse` 훅은 Codex에서도 실행된다고 가정하지 않는다. 공통 검증을 Git 훅/CI에서 실행할 수 있도록 분리하고, 도구별 실행 전 검사는 보조 수단으로 둔다.
- 커밋 접두어·Refs는 commit-msg/CI, PR base는 CI, 대량 스테이징 금지는 에이전트 지침/도구별 검사로 구분한다. Git 훅으로 과거 `git add .` 사용 자체를 감지할 수 있다고 약속하지 않는다.
- 새 원본의 '기본 브랜치 main / 개발 브랜치 dev' 모델과 현 프로젝트 모델의 차이를 어댑터에 명시한다. 원본 checker는 그대로 복사하지 않는다.

완료 기준: 잘못된 커밋 trailer와 PR base를 잡는 검증, 올바른 커밋·PR 허용을 확인한다. 환경에 설치되지 않은 훅은 적용 완료로 표시하지 않는다.

## 검토 및 인수 조건

- 변경 전후 규칙 검색으로 Notion/Gemini/Obsidian 의무, 위키 역링크 의무, 자동 amend, 강제 삭제, `.Codex` 오경로 잔존을 확인한다.
- 새 이슈 하나를 읽고 관련 스펙과 다음 행동을 찾는 재개 시나리오를 확인한다.
- 기존 세계관 변경, stash, 원격 OCI 브랜치가 유지됨을 확인한다.
- 설정·문서 전환만으로 제품 기능 테스트 전체를 다시 돌리지 않는다. 검사 스크립트를 추가/변경할 때 허용·거부 케이스를 검증한다.
- 본 계획은 문서·작업 관리 전환 계획이며 제품 코드 구현 계획이 아니다. 실제 전환은 별도 요청 후 진행한다.

## 되돌리기

전환 설정은 별도 변경으로 묶는다. 문제가 생기면 설정 변경만 되돌리고 기존 문서·이슈·코드 WIP는 유지한다. 과거 기록 보존을 위해 rebase/reset/force push로 히스토리를 다시 쓰지 않는다.
