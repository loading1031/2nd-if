# 리더 경험·리뷰 기준

이 문서는 기존 사용자 피드백을 프로젝트 안에서 공유하기 위해 옮긴 기준이다. 최신 스타일 명세와 제품 결정을 함께 읽는다. 아래 기술 예시는 당시 품질 한계에 대한 맥락이며 모든 장면에 특정 렌더링 기술을 강제하지 않는다.

## 모션 철학

PoC v3에서 "용이 입자로 분해되어 흩날리는" 연출을 만들었더니 사용자가 "애니메이션 효과를 너무 크게 할 필요 없어. 난이 있으면 난이 살랑거리는 것만으로 충분. 용이 흩날리는 게 아니라 움직이면서 글자를 밀어내는 것만으로 좋아. 중요한 건 깔끔해야 해. 글이니까. 번잡하지 않고"라고 바로잡음.

**Why:**
2nd-if는 **읽는 경험**이 본질이고, 리더는 **글이 주인공**. 시네마틱/파티클/불꽃 같은 크고 화려한 모션은 주의력을 글에서 빼앗아서 제품의 존재 이유를 배반함. 사용자가 원하는 건 "책처럼 조용하고 우아하게 움직이는 페이지"이지 "인터랙티브 뮤직비디오"가 아님. Pretext의 진짜 정체성도 텍스트 리플로우 엔진이지, 파티클 엔진이 아님 — 오브젝트가 **살짝** 움직이면 텍스트가 **자동으로 따라 재배치**되는 것이 핵심 연출. 그 자체로 충분히 감탄스러움.

**How to apply:**

1. **모션의 기본 단위 = 미세**:
   - 난초가 있으면 잎이 살랑 (±3~5px, 2~4초 주기)
   - 용이 있으면 몸통이 천천히 구부러짐 (수 초 주기의 sin 변형)
   - 구름이 있으면 아주 느리게 옆으로 흐름
   - 눈/비 파티클이면 정말 적은 양(몇 십 개), 느린 낙하

2. **Pretext의 핵심 가치**: 오브젝트 bounds가 미세하게 변하면 **layoutNextLine()의 라인 폭이 실시간으로 재계산됨**. 텍스트가 오브젝트 실루엣을 따라 살짝 밀렸다 돌아옴 → 이게 제품의 "살아있는 느낌". 다른 효과 필요 없음.

3. **큰 전환의 장면화 금지**:
   - ❌ 용이 돌진하며 글자를 불태움 (v2에서 한 실수)
   - ❌ 용이 입자로 분해되어 페이지를 가로지름 (v3에서 한 실수)
   - ✅ 페이지 넘길 때 부드러운 가로 슬라이드 + 부드러운 페이드 (400~600ms, ease-in-out)
   - ✅ 오브젝트 위치가 새 스프레드에서 바뀔 때는 **크로스페이드만** (옛 것 페이드 아웃, 새 것 페이드 인, 겹치는 400ms)

4. **"깔끔" 체크리스트** (매 PoC 마다 자기 검증):
   - 가운데 두고 봤을 때 **어디에 시선이 가는가?** 일러스트면 실패. 글이어야 함.
   - 모션 중 **글자가 들리는가?** 읽을 수 있어야 함. 글자가 흔들리면 실패.
   - 모션 주기가 몇 초인가? **<1초면 너무 빠름**. 2~4초가 기본.
   - 화면 동시에 움직이는 요소가 **3개 이상이면 번잡**.

5. **책의 레퍼런스 = 전자책, 종이책**: Apple Books, Readwise, Kindle의 페이지 넘김을 떠올려라. 그 수준 이상의 모션은 넣지 말 것. 인터랙티브 데모(Pretext showcase의 일부)는 "기술 데모"라 화려하지만, 우리는 "매일 쓰는 리더"이므로 다른 기준.

6. **이 원칙이 무너지는 유일한 예외**: 사용자가 **명시적으로** "이 장면은 시네마틱해야 한다"고 요청한 경우 (예: 작가가 특정 단락에 "전투 장면" 같은 명시적 주석을 달았을 때). 기본은 고요함.

## 품질 기준과 당시 구현의 한계

PoC v3의 래스터 잉크 파티클 애니메이션을 보여줬을 때 사용자가 "진짜 조잡하군"이라고 평가. 동의. 현재 구현은 `fillRect` 기반 포인트 스프라이트라 **잉크가 아니라 모래**로 보임.

**Why:**
2nd-if는 "태블릿/PC에서 책처럼 읽는 웹소설"로 포지셔닝. 리더의 시각/모션 품질 자체가 제품 차별화 포인트라, "동작은 한다" 수준으로는 부족. 레퍼런스(Chen Rong 九龍圖, Birdabo 데모)와 나란히 놓고도 부끄럽지 않아야 함. "조잡한" 결과를 "구현은 됐으니 통과"로 처리하면 제품 정체성이 무너짐.

**How to apply:**

1. **자각**: 리더/애니메이션 관련 작업은 Canvas 2D + 단순 파티클로는 품질 한계가 있다는 것을 기본 전제로 깔 것. 수준급 결과를 내려면:
   - WebGL/WebGPU 기반 파티클 인스턴싱 + Gaussian 스플랫
   - curl noise 같은 유체 속도장
   - 누적 버퍼 + 블러 + 임계치 리매핑 (2-pass render)
   - 진짜 brush-tip 텍스처
   - feathered alpha / ink-on-paper 쉐이더
   이런 것들이 "이 제품이 요구하는 수준"임을 잊지 말 것.

2. **리뷰어 설정**: 시각 품질을 평가하는 전용 서브에이전트가 필요. 이름 후보: `reader-aesthetic-reviewer`. 입력은 PoC URL + 무드보드 디렉토리 + 스타일 가이드. 작업은 스크린샷을 레퍼런스와 나란히 비교해서 구체적으로 "이 지점이 레퍼런스와 다르다"고 지적. 내가 PoC 수정할 때마다 수동 발동으로 호출.

3. **스킬 로드맵**: 사용자가 "계속 갈고 닦아야 한다"고 명시. 이 도메인에서 배울 것:
   - WebGL 파티클 시스템 (instanced rendering, transform feedback)
   - Shader로 잉크 표현 (SDF, alpha feather, ink bleed simulation)
   - Live2D/Spine2D 같은 2D 스켈레톤 애니메이션
   - Fluid simulation (Stable Fluids, SPH)
   - 실제 아티스트 협업 구조 (Photoshop brush, Procreate 등의 에셋 파이프라인)

4. **평가 기준**: "구현 성공" ≠ "통과". 완성된 PoC는 반드시 **무드보드 Top 5 레퍼런스와 나란히** 놓고 자체 평가할 것. 스킬 갭이 보이면 사용자에게 솔직히 "이 수준은 아직 부족하다, 다음 단계는 X 기술이 필요하다"고 말할 것. 미화 금지.

## 화면 크기와 타깃

2nd-if 리더의 핵심 경험(펼침면 레이아웃 + Pretext 페이지 분할 + 일러스트면)은 **태블릿/PC 우선**으로 설계된다. 폰은 "읽을 수는 있는 폴백" 수준만 보장.

**Why:**
경쟁 플랫폼(네이버웹툰, 카카페, 문피아)은 모두 모바일 퍼스트. 이 제품은 "태블릿/PC에서 책처럼 읽는 웹소설"로 포지셔닝해서 차별화. 양면 펼침 + 일러스트면 + 페이지 넘김은 큰 화면에서만 작동하는 연출이라 모바일 퍼스트 가정이 깨진 순간 제품 정체성이 성립.

**How to apply:**
- 뷰포트 타깃: 데스크톱 ≥1280px (이상) / 태블릿 가로 1024~1279px (주) / 태블릿 세로 768~1023px (지원) / 폰 <768px (클래식 모드 강제).
- UX 설계 시 "모바일에서 어떻게 보이나" 질문보다 "iPad 가로에서 어떻게 보이나"를 먼저.
- 본문 폰트 기본 18~20px, 일러스트 권장 1600~2400px 폭.
- 폰 대응 로직에 과도한 시간 투입 금지. 폰 사용자는 안내 문구("태블릿/PC에서 더 아름답게") + 클래식 모드로 처리.
- 랜딩/마케팅에서도 태블릿 언급.
